# Chapter 3

Chapter 3 — Active Directory Network Foundations, Identity Communications, and Protocol Security 3.1 Identity Infrastructure Is Network Infrastructure 3.1.1 Authentication Does Not Occur in Isolation Active Directory authentication depends upon network reachability, service discovery, name resolution, time synchronization, protocol negotiation, and communication with trusted identity infrastructure. 3.1.2 Identity Protocols as Network Traffic Kerberos, Lightweight Directory Access Protocol (LDAP), Server Message Block (SMB), Remote Procedure Call (RPC), Domain Name System (DNS), Network Time Protocol (NTP), Remote Authentication Dial-In User Service (RADIUS), certificate enrollment, and federation protocols ultimately traverse networks whose configuration affects their security. 3.1.3 Availability of the Network Versus Integrity of the Identity Path Successful packet delivery does not prove that an authentication path is trustworthy. Name resolution manipulation, relaying, interception, protocol downgrade, routing changes, and unauthorized intermediaries can preserve connectivity while undermining identity assurance. 3.1.4 Network Position as an Identity-Security Advantage An adversary able to observe, redirect, influence, or impersonate network services may gain opportunities to capture authentication exchanges, coerce credentials, relay authentication, manipulate service discovery, or redirect users toward attacker-controlled infrastructure. 3.1.5 FICAM and the Identity Communications Path Identity assurance depends not only on credentials and authenticators but also on whether the infrastructure transporting identity transactions preserves confidentiality, integrity, authenticity, and appropriate trust boundaries. 3.1.6 Zero Trust Does Not Eliminate Network Dependencies Zero Trust reduces reliance on network location as proof of trust, but identity providers, policy engines, devices, directories, applications, and enforcement points still require secure communications between them. 3.2 TCP/IP Foundations for Identity Services 3.2.1 Internet Protocol Addressing in Active Directory Environments Internet Protocol Version 4 (IPv4) and Internet Protocol Version 6 (IPv6) addressing provide the basic reachability upon which directory discovery, authentication, replication, administration, and application access depend. 3.2.2 Transmission Control Protocol and User Datagram Protocol Identity services use both connection-oriented Transmission Control Protocol (TCP) and connectionless User Datagram Protocol (UDP), making transport behavior relevant to authentication reliability, firewall policy, troubleshooting, and defensive monitoring. 3.2.3 Sessions, Connections, and State Understanding connection establishment, session state, retransmission, timeout behavior, and service listeners helps distinguish application-layer authentication problems from underlying transport failures. 3.2.4 Maximum Transmission Unit, Fragmentation, and Authentication Traffic Large authentication messages, especially Kerberos exchanges containing substantial authorization data, may interact with Maximum Transmission Unit (MTU) limits and transport fallback behavior. 3.2.5 IPv4 and IPv6 Coexistence Windows environments commonly operate dual-stack networking even where administrators primarily manage IPv4, creating security implications when IPv6 behavior is ignored rather than intentionally governed. 3.2.6 Network Address Translation and Identity-Aware Services Network Address Translation (NAT), proxies, gateways, load balancers, and other intermediaries can affect source attribution, protocol behavior, certificate validation, federation flows, and security telemetry. 3.3 Routing, Segmentation, and Identity Reachability 3.3.1 Routing as a Security Dependency Routing determines which systems can communicate with domain controllers, certification authorities, federation services, management systems, cloud connectors, and other identity infrastructure. 3.3.2 Network Segmentation Versus Administrative Segmentation Placing systems on separate networks does not create an effective administrative boundary when credentials, management services, trust relationships, or privileged accounts cross those boundaries. 3.3.3 Tier 0 Network Isolation Domain controllers and other control-plane systems require communication patterns different from ordinary servers and endpoints because compromise of their network-access pathways can expose identity authority. 3.3.4 Management Plane Separation Administrative protocols, management interfaces, remote execution services, backup systems, hypervisors, monitoring platforms, and configuration-management systems create privileged communications paths that must be considered separately from ordinary application traffic. 3.3.5 East-West Identity Traffic Internal traffic between workstations, servers, domain controllers, management platforms, and shared services creates lateral-movement opportunities that perimeter-focused security models frequently overlook. 3.3.6 North-South and Hybrid Identity Traffic Cloud identity, federation, remote access, Software as a Service (SaaS), external partners, and hybrid synchronization create identity paths that cross traditional enterprise network boundaries. 3.3.7 Microsegmentation and Identity-Aware Enforcement Zero Trust architectures increasingly combine network segmentation with identity, device, application, workload, and contextual information rather than granting broad reachability based solely on subnet membership. 3.4 Ports, Services, and Active Directory Communications Dependencies 3.4.1 Active Directory's Distributed Service Model Active Directory does not depend upon a single network port. Authentication, directory access, service discovery, replication, Group Policy, administration, and supporting infrastructure use multiple interconnected services. 3.4.2 Core Active Directory Service Ports Readers are introduced to the roles commonly associated with DNS, Kerberos, LDAP, LDAP over TLS, SMB, RPC, Global Catalog services, NTP, and other Active Directory communications. 3.4.3 Static Ports Versus Dynamic RPC Ports Some Windows services use well-known ports for initial contact and dynamically assigned ports for subsequent RPC communication, creating important firewall and segmentation considerations. 3.4.4 Global Catalog Communications Global Catalog services support forest-wide directory searches and identity resolution across domain boundaries through dedicated LDAP-compatible service ports. 3.4.5 Network Access Authentication Ports RADIUS, Terminal Access Controller Access-Control System Plus (TACACS+), Extensible Authentication Protocol (EAP)-related infrastructure, and network-access systems expand the identity communications surface beyond domain-controller protocols. 3.4.6 Certificate and Federation Communications Certificate enrollment, revocation checking, federation metadata, token exchange, cloud authentication, and hybrid identity introduce additional Hypertext Transfer Protocol Secure (HTTPS), RPC, and application-specific communication requirements. 3.4.7 Building a Dependency Matrix Instead of Memorizing Port Numbers The operational objective is not memorization. Practitioners must understand which identity function requires a communication path, which systems participate in it, what security property the protocol provides, and what breaks when the path is altered or blocked. 3.5 Domain Name System as Identity Infrastructure 3.5.1 Why Active Directory Depends on DNS Active Directory clients use DNS to discover domain controllers, Kerberos services, Global Catalogs, and other domain resources. 3.5.2 Active Directory-Integrated DNS Active Directory-integrated zones use directory replication and access-control mechanisms that make DNS configuration part of the identity security model. 3.5.3 Service Location Records Service (SRV) records allow clients to locate Key Distribution Centers (KDCs), LDAP services, Global Catalogs, and domain controllers appropriate to a domain or site. 3.5.4 Domain Controller Locator Windows clients combine DNS queries, site information, domain knowledge, and service records to locate suitable domain controllers. 3.5.5 Dynamic DNS Updates Secure dynamic updates enable domain members and authorized services to maintain records while reducing opportunities for unauthorized name registration. 3.5.6 DNS Record Ownership and Access Control Permissions over DNS objects can affect whether principals may create, replace, modify, or delete records used by identity-aware services. 3.5.7 Name Resolution Manipulation as an Identity Attack Primitive Redirecting a trusted hostname toward an attacker-controlled system may convert an ordinary lookup failure into credential capture, authentication coercion, interception, or relay opportunity. 3.5.8 DNS Logging and Defensive Visibility Query logging, record-change auditing, endpoint telemetry, and directory-service events can reveal unexpected name registrations, unusual service discovery, and infrastructure manipulation. 3.6 Windows Name Resolution Beyond DNS 3.6.1 Why Fallback Name Resolution Still Matters Legacy and local name-resolution mechanisms remain present in many Windows environments and may activate when normal DNS resolution fails. 3.6.2 Link-Local Multicast Name Resolution Link-Local Multicast Name Resolution (LLMNR) allows neighboring systems to answer local multicast queries without authoritative DNS verification. 3.6.3 NetBIOS Name Service NetBIOS Name Service (NBT-NS) represents an older Windows naming mechanism that can still expose authentication traffic in legacy or poorly hardened environments. 3.6.4 Multicast DNS Multicast DNS (mDNS) expands local service discovery and must be evaluated according to the systems and applications present within an enclave. 3.6.5 Web Proxy Auto-Discovery Web Proxy Auto-Discovery (WPAD) can interact with DNS, Dynamic Host Configuration Protocol (DHCP), and fallback resolution behavior in ways that create opportunities for traffic redirection and authentication capture. 3.6.6 Poisoning and Rogue Response Concepts Unauthenticated local name-resolution mechanisms may allow an attacker to answer queries faster than legitimate infrastructure and induce systems to communicate with an unauthorized endpoint. 3.6.7 Defensive Elimination of Unnecessary Fallback Protocols Where mission and application requirements permit, unnecessary fallback name-resolution mechanisms should be disabled rather than left available indefinitely for compatibility that no longer exists. 3.7 IPv6, DHCPv6, and Identity Traffic Redirection 3.7.1 Windows IPv6 Behavior IPv6 is normally enabled in modern Windows systems and can influence routing, DNS selection, local discovery, and service communication even in environments administered primarily as IPv4 networks. 3.7.2 Stateless Address Autoconfiguration Stateless Address Autoconfiguration (SLAAC) allows hosts to derive IPv6 addressing information from local network advertisements. 3.7.3 Router Advertisements and Trust Unauthorized Router Advertisements (RAs) can alter how systems identify gateways and reach network resources. 3.7.4 DHCPv6 and DNS Assignment Rogue Dynamic Host Configuration Protocol Version 6 (DHCPv6) responses can influence DNS configuration and redirect clients toward attacker-controlled name-resolution infrastructure. 3.7.5 IPv6 as an Overlooked Attack Surface Security programs that ignore IPv6 rather than deliberately configuring it may leave a functional communications plane outside expected monitoring and hardening practices. 3.7.6 Defensive IPv6 Governance Router Advertisement Guard, DHCPv6 Guard, endpoint controls, switch protections, firewall rules, and monitoring should reflect the environment's intentional IPv6 architecture. 3.8 Time Synchronization and Identity Assurance 3.8.1 Why Identity Systems Care About Time Authentication protocols, certificates, tokens, logs, replication, forensic timelines, and distributed security controls depend upon reasonably synchronized clocks. 3.8.2 Kerberos Clock Skew Kerberos uses time as part of replay protection, making excessive clock differences capable of producing authentication failures. 3.8.3 The Active Directory Time Hierarchy Domain members ordinarily derive time through the domain hierarchy, with the forest-root Primary Domain Controller Emulator occupying a critical position in authoritative time synchronization. 3.8.4 External Time Sources The authoritative domain time source must ultimately obtain reliable time from approved upstream sources appropriate to the mission environment. 3.8.5 Time Manipulation as a Security Problem Unexpected time changes may disrupt authentication, invalidate certificates, affect logs, complicate incident reconstruction, or interfere with security controls that depend upon temporal ordering. 3.8.6 Time Integrity in Disconnected and Tactical Environments Disconnected, degraded, intermittent, and limited-bandwidth environments require deliberate time architecture because ordinary external synchronization assumptions may not hold. 3.9 Server Message Block and Identity Communications 3.9.1 SMB in Windows Enterprise Environments Server Message Block supports file access, administrative shares, Group Policy retrieval, SYSVOL, NETLOGON, named pipes, and numerous Windows management activities. 3.9.2 SMB Versions and Security Evolution The security properties of SMB have changed substantially from legacy SMBv1 through modern SMBv2 and SMBv3 implementations. 3.9.3 SMB Authentication SMB commonly interacts with Kerberos and New Technology LAN Manager (NTLM), making its authentication configuration relevant to both credential security and lateral movement. 3.9.4 SMB Signing Message signing provides integrity and helps prevent alteration or unauthorized relaying of authenticated SMB communications. 3.9.5 SMB Encryption Modern SMB implementations can provide payload confidentiality in addition to authentication and integrity. 3.9.6 Administrative Shares and Remote Management Exposure Shares such as `ADMIN$`, `C$`, `SYSVOL`, and `NETLOGON` serve legitimate administrative or domain functions while also providing information and execution pathways that require appropriate access controls. 3.9.7 SMB as a Relay and Lateral-Movement Surface Where signing, authentication, privilege, and network reachability permit, SMB can become part of credential relay, remote administration, execution, and lateral-movement paths. 3.10 Remote Procedure Call and Distributed Windows Authority 3.10.1 Why RPC Matters to Active Directory Remote Procedure Call underpins numerous Windows administrative, authentication, replication, certificate, service-management, and directory operations. 3.10.2 RPC Endpoint Mapper Clients commonly contact the RPC Endpoint Mapper before connecting to dynamically assigned service endpoints. 3.10.3 Dynamic RPC Port Allocation Modern Windows systems use high-numbered dynamic ports for many RPC interfaces, complicating simplistic firewall policies based solely on TCP 135. 3.10.4 Named Pipes and RPC Over SMB Some RPC services communicate through named pipes carried over SMB, illustrating how Windows protocols are frequently layered rather than independent. 3.10.5 RPC Interfaces as Security Boundaries Individual RPC interfaces expose different operations and authorization requirements, meaning that network reachability to RPC does not imply identical access to every function. 3.10.6 Authentication Coercion as an RPC Security Concept Some legitimate RPC functions can be abused to cause another system to initiate outbound authentication, turning ordinary service behavior into an identity-attack primitive. 3.10.7 Restricting RPC Reachability Tiering, host firewalls, network access controls, service reduction, and management-plane isolation can reduce unnecessary exposure without breaking required identity communications. 3.11 LDAP Transport Security Foundations 3.11.1 LDAP as the Directory Communications Protocol Lightweight Directory Access Protocol provides the principal interface through which applications, administrators, and systems query and modify Active Directory objects. 3.11.2 LDAP and Secure LDAP LDAP may operate through authenticated protocol security mechanisms or through Transport Layer Security (TLS), including LDAP over TLS commonly referred to as LDAPS. 3.11.3 LDAP Binding Directory clients must establish an authentication context before performing operations that require an identified security principal. 3.11.4 LDAP Signing LDAP signing protects message integrity and reduces opportunities for manipulation and certain authentication-relay attacks. 3.11.5 LDAP Channel Binding Channel Binding Tokens (CBTs) associate authentication with the underlying TLS channel and strengthen protection against credential relay. 3.11.6 Simple Binds and Cleartext Credential Risk Credential-based simple binds require transport protection because authentication secrets can otherwise traverse the network without adequate confidentiality. 3.11.7 LDAP as Both an Administrative and Offensive Surface The same directory interface used for legitimate discovery and administration can expose information about users, groups, computers, privileges, trusts, delegation, certificates, and other relationships useful to an adversary. 3.11.8 Preparing for Deeper Directory Protocol Analysis This chapter establishes LDAP's network role; later chapters examine searches, filters, controls, directory structures, security descriptors, and offensive enumeration in substantially greater depth. 3.12 Kerberos Communications Foundations 3.12.1 Kerberos as a Network Authentication Protocol Kerberos depends upon reliable communications among clients, Key Distribution Centers, and target services. 3.12.2 Key Distribution Center Discovery Clients use Active Directory and DNS service discovery to locate appropriate KDC services. 3.12.3 Authentication Service and Ticket Granting Service Traffic The Authentication Service (AS) and Ticket Granting Service (TGS) exchanges establish the basic network flow through which clients acquire Ticket Granting Tickets (TGTs) and service tickets. 3.12.4 Kerberos Over UDP and TCP Kerberos implementations can use UDP or TCP, with message size and platform behavior influencing transport selection. 3.12.5 Service Principal Names and Network Service Identity Service Principal Names (SPNs) connect Kerberos authentication to identifiable network service instances. 3.12.6 Network Conditions That Trigger Authentication Fallback Name-resolution failures, SPN problems, service configuration, legacy dependencies, or application behavior may cause environments to fall back from Kerberos to NTLM. 312.7 Why Fallback Matters A service that unexpectedly authenticates through NTLM may expose security properties substantially different from those expected under Kerberos. 3.12.8 Preparing for Deep Kerberos Analysis Ticket cryptography, the Privilege Attribute Certificate (PAC), delegation, PKINIT, ticket attacks, Kerberoasting, and other advanced mechanics are developed in their dedicated chapters. 3.13 NTLM and Legacy Authentication on the Network 3.13.1 Why NTLM Still Exists Backward compatibility, legacy applications, local authentication, name-resolution failures, workgroup systems, and configuration dependencies continue to produce NTLM traffic in modern Windows environments. 3.13.2 Challenge-Response Authentication NTLM avoids directly transmitting a plaintext password but relies upon a challenge-response protocol whose security properties differ significantly from modern ticket- and certificate-based authentication. 3.13.3 NetNTLM Versus Stored NT Hashes Network challenge-response material and the underlying NT password hash are related but distinct artifacts and must not be treated as interchangeable concepts. 3.13.4 NTLMv1 and NTLMv2 NTLMv2 improves significantly upon NTLMv1 but does not eliminate credential interception, offline password attacks, authentication coercion, or relay concerns. 3.13.5 Authentication Relaying An adversary may attempt to forward a valid authentication exchange toward another service rather than recover the user's password. 3.13.6 Auditing Before Restricting NTLM Enterprises should identify legitimate NTLM dependencies before enforcing restrictions that may disrupt applications or mission services. 3.13.7 Strategic NTLM Reduction The long-term objective is not simply disabling a protocol switch. Dependencies must be identified, applications corrected, stronger authentication made available, and remaining exceptions deliberately governed. 3.14 Network Access Authentication 3.14.1 Identity at the Network Edge Enterprise networks often authenticate users and devices before granting connectivity through wireless, wired, Virtual Private Network (VPN), and remote-access infrastructure. 3.14.2 RADIUS Architecture Remote Authentication Dial-In User Service separates the access device from the authentication and authorization decision and is widely used for centralized network-access control. 3.14.3 Microsoft Network Policy Server Network Policy Server (NPS) provides Microsoft's RADIUS implementation and can integrate Active Directory identities, certificate authentication, network policy, and accounting. 3.14.4 TACACS+ Terminal Access Controller Access-Control System Plus provides centralized authentication, authorization, and accounting commonly associated with administrative access to network infrastructure. 3.14.5 Authentication, Authorization, and Accounting Network access systems make the distinction between proving identity, granting a permitted form of access, and recording what occurred especially visible.

# 1.5.7 Technical Findings Must Be Translated Into Mission Meaning

The final rule is that technical findings must be expressed in terms that preserve technical accuracy while communicating operational significance.

This is especially important in federal and military environments because identity-security remediation competes for resources, maintenance windows, personnel, funding, and mission priority.

A technically precise finding can still fail if its consequence is poorly communicated.

For example:

"Authenticated Users have `WriteDACL` over Object X"

may be accurate.

It does not yet explain the risk.

A stronger analysis asks what control of Object X enables.

If Object X is a group that controls a Group Policy Object linked to Domain Controllers, the full attack path may be:

Authenticated user\
→ modifies Object X's DACL\
→ gains control of privileged group membership\
→ acquires control over a GPO\
→ modifies policy applied to Domain Controllers\
→ executes code under highly privileged context\
→ gains effective control over the domain's identity infrastructure.

The initial permission is only the first edge.

The mission consequence lies at the end of the path.

A mature practitioner should therefore be able to translate the same finding for several audiences.

For the Active Directory engineer, the finding should identify the exact object, permission, inheritance path, and configuration requiring correction.

For the penetration tester, it should describe how the control relationship can be traversed.

For the defender, it should identify the control that breaks the path.

For the SOC analyst, it should identify the evidence expected if the path is exercised.

For the assessor, it should identify the evidence required to demonstrate remediation.

For the Authorizing Official or mission owner, it should explain what mission capability could be affected if the identity-control path is exploited.

The technical facts must remain the same.

Only the language and level of abstraction change.

This ability to translate identity risk across technical, operational, governance, and mission contexts is not a secondary communication skill.

It is part of identity security engineering itself.

A finding that cannot be translated may never receive the priority required to be fixed.

A finding that is exaggerated may lose credibility.

A finding that is technically correct but operationally meaningless may consume resources without reducing real risk.

The practitioner must therefore understand not only how to discover identity weaknesses, but how to explain why they matter.

That principle will remain visible throughout Contested Terrain.

# 1.3.5 Command-Line and Scripting Familiarity

Identity engineering and identity security both rely heavily on command-line interfaces and scripting.

PowerShell is especially important because Windows and Active Directory administration expose enormous amounts of directory and security functionality through PowerShell modules, .NET interfaces, Windows APIs, and remote management capabilities.

Offensive security tools frequently automate those same legitimate mechanisms.

Readers should therefore be comfortable reading command-line syntax and interpreting parameters, object names, distinguished names, paths, and command output. They are not expected to memorize every command presented in the book.

The commands exist to expose mechanics.

When a PowerShell command queries an object's access control list, the important lesson is not the cmdlet syntax. The important lesson is what object is being queried, where its security descriptor is stored, what permissions are being returned, and what those permissions mean.

When Rubeus requests a Kerberos ticket, the important lesson is not which switch was typed. The important lesson is which Kerberos exchange occurred, what key material was used, what ticket was returned, and why the environment accepted the request.

When Certipy or Certify identifies a vulnerable certificate template, the important lesson is not the color of the output or the name of the detection rule. The important lesson is which template properties, enrollment permissions, Extended Key Usages (EKUs), subject-name controls, and Certification Authority (CA) conditions combine to create unintended authentication authority.

Tools should accelerate understanding, not replace it.

This distinction also makes the reader more resilient professionally. Tools change. Projects are abandoned. Syntax changes. Endpoint protections block binaries. Detection signatures improve. New tools appear.

The security relationship underneath the tool usually remains.

# 5.5.1 Personal Identity Verification

Personal Identity Verification (PIV) establishes the federal common identity credential defined under Homeland Security Presidential Directive 12 (HSPD-12) and standardized through FIPS 201. FIPS 201-3 defines the architecture and technical requirements for PIV credentials used by federal employees and contractors to support authentication for federally controlled facilities, information systems, and applications. ([2](https://csrc.nist.gov/pubs/fips/201-3/final))

The significance of PIV to identity security lies in the relationship between the physical credential, the certificates and cryptographic keys associated with it, and the identity-proofing and issuance processes that precede its use.

A PIV card is not simply a badge that happens to contain a computer chip. It is a cryptographic credential operating within a larger federal trust architecture. The card can contain asymmetric key pairs and certificates supporting authentication and other approved uses, while the surrounding PKI allows relying systems to validate the certificate chain and determine whether the credential was issued by an authority they trust. ([3](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.201-3.pdf))

When PIV is used for Windows domain authentication, this trust architecture intersects with Active Directory through smart-card logon and Public Key Cryptography for Initial Authentication in Kerberos (PKINIT). The user proves possession of the private key associated with the authentication certificate rather than transmitting or deriving the authentication decision solely from the account password. Domain Controllers participating in the authentication process must themselves be appropriately certificate-enabled, and Windows must be able to associate the presented certificate with the intended account. Federal implementation guidance for PIV smart-card logon on Windows domains explicitly identifies Domain Controller authentication certificates as part of that architecture. ([4](https://www.idmanagement.gov/implement/scl-windows/))

This changes the attack surface but does not remove it.

Password-focused attacks become less central to the particular authentication ceremony, but the security dependency moves into certificate issuance, certificate mapping, private-key protection, trusted Certification Authorities, revocation, Domain Controller configuration, and alternate authentication mechanisms retained by the account.

That distinction is critical. A PIV-enabled account may still possess a password because Active Directory and dependent applications may require password-derived cryptographic material for functions unrelated to the PIV logon ceremony. Legacy applications may also preserve alternate authentication paths. The presence of a PIV credential therefore should not be interpreted as evidence that password and credential-management risks have disappeared from the account.

The security architecture has added a stronger authentication path.

Whether weaker parallel paths remain is a separate engineering question.

#### PIV Authentication and Directory Authority

PIV also illustrates why authentication assurance and authorization must remain separate.

Successful PIV authentication establishes strong evidence that the claimant controls the cryptographic credential associated with the represented identity. It says nothing by itself about whether that account should possess privileged Active Directory rights.

A PIV-authenticated user can still be a member of an inappropriate administrative group.

A PIV-authenticated service administrator can still log on to an inappropriate tier.

A PIV-authenticated identity can still possess `WriteDACL`, `GenericAll`, replication rights, certificate-template control, or another dangerous permission.

The authentication mechanism makes unauthorized impersonation more difficult.

It does not correct excessive authorization.

This distinction becomes particularly important in federal security assessments, where successful deployment of smart-card authentication can create an understandable but dangerous sense that the associated identity has become inherently safer. Authentication is stronger. The identity's effective authority still has to be examined independently.

#### PIV Trust Is Dependent on Certificate Validation

The cryptographic strength of PIV authentication also depends on the relying system validating the credential correctly.

Certificate validation is not equivalent to verifying that a certificate contains an expected-looking subject name. The relying environment must establish an acceptable chain of trust, evaluate the certificate for the intended authentication purpose, and process applicable validity and revocation information. The technical details are developed in Chapters 19 and 20, where the PKI and smart-card architecture is examined directly.

For the current discussion, the important point is that PIV moves part of the authentication trust decision into PKI.

That makes PKI security identity security.

A Domain Controller may be perfectly hardened against password attacks while still depending upon certificate infrastructure whose compromise can affect which identities it is willing to authenticate.

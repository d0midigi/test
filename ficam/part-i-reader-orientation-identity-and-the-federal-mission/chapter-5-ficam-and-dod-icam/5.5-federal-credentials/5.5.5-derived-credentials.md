# 5.5.5 Derived Credentials

Federal credentialing cannot assume that every access scenario can use a physical PIV card directly.

Mobile platforms, specialized devices, modern authentication architectures, and operational circumstances may make the original smart-card form factor impractical while still requiring identity assurance derived from the established PIV identity.

Derived PIV credentials address this problem.

FIPS 201-3 recognizes derived PIV credentials as additional PIV credentials issued based on an existing PIV identity relationship, and NIST SP 800-157 Revision 1 provides current technical guidance for their use. NIST describes derived PIV credentials as additional common identity credentials issued by federal departments or agencies for circumstances in which direct use of the PIV Card is impractical. ([3](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.201-3.pdf))

The word _derived_ should not be interpreted as copied.

A secure derived-credential architecture does not simply export the original card's private key onto another device. The derived credential establishes an additional authenticator associated with the already-established federal identity under defined issuance and lifecycle requirements.

This distinction is important because modern identity security increasingly requires one enterprise identity to support several authenticators.

A user may possess a PIV card, a derived credential on an approved mobile device, a FIDO authenticator, or another authorized authentication mechanism depending on system requirements and policy.

The resulting security problem is not simply whether each authenticator is individually strong.

The enterprise must maintain consistent lifecycle control across all of them.

If the subject separates, each associated authenticator must cease to provide unauthorized access.

If one authenticator is lost, revoking it should not unnecessarily destroy every other valid authenticator.

If a replacement authenticator is enrolled, the enrollment process must prevent an attacker from attaching their own credential to an already trusted identity.

Modern credential governance is therefore increasingly a problem of managing authenticator sets rather than one user, one password, one credential.

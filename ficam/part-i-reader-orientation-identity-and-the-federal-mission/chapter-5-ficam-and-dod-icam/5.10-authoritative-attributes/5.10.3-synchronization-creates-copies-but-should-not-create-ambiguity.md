# 5.10.3 Synchronization Creates Copies but Should Not Create Ambiguity

Enterprise ICAM depends heavily on synchronization and provisioning because identity information must often be consumed by systems that do not share the same native data store.

The moment an authoritative attribute is copied, however, the architecture acquires another state-management problem.

Which copy wins when values differ?

Can the downstream value be edited locally?

Does a writeback mechanism exist?

What happens if the authoritative source becomes unavailable?

How quickly does revocation propagate?

Can a stale value continue authorizing access while synchronization is broken?

These are not merely integration questions.

They determine how long the identity system can remain wrong without anyone noticing.

A synchronization failure can therefore create two very different operational conditions.

The obvious failure is that updates stop moving.

The more dangerous failure is that the system continues operating using stale identity state.

Nothing appears unavailable.

The access decision has simply become progressively less authoritative.

This is particularly significant for termination, privilege removal, sponsorship expiration, and other lifecycle changes in which delay directly extends unauthorized access.

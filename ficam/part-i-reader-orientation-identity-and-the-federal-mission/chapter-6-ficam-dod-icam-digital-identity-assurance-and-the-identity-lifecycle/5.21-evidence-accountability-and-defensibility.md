# 5.21 Evidence, Accountability, and Defensibility

## 5.21 Evidence, Accountability, and Defensibility

### 5.21.1 Federal Security Decisions Must Be Explainable

{% hint style="info" %}
Practitioners should be able to explain why an identity control exists, what authority requires it, how it is implemented, who is responsible, and how effectiveness is verified.
{% endhint %}

### 5.21.2 Evidence Must Represent the Environment That Exists

{% hint style="info" %}
Outdated diagrams, inherited control statements, screenshots from previous releases, copied implementation language, and stale scans cannot substitute for evidence of the current environment.
{% endhint %}

### 5.21.3 Exceptions Must Remain Visible

{% hint style="info" %}
Risk acceptance does not remove a technical condition. Approved deviations should remain documented and monitored so they do not become permanent invisible weaknesses.
{% endhint %}

### 5.21.4 Technical Debt Is Also Governance Debt

{% hint style="info" %}
Legacy authentication, unsupported applications, stale trusts, old service accounts, unmanaged certificates, and excessive privilege create risk that policy documentation alone cannot eliminate.
{% endhint %}

### 5.21.5 Accountability Includes Remediation

{% hint style="info" %}
Discovering and documenting a weakness is only one stage of governance. Remediation ownership, milestones, validation, and risk decisions must follow.
{% endhint %}

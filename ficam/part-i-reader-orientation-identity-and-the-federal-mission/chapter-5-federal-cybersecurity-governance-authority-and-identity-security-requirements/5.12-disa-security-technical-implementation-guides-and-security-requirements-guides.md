# 5.12 DISA Security Technical Implementation Guides and Security Requirements Guides

## 5.12 DISA Security Technical Implementation Guides and Security Requirements Guides

### 5.12.1 STIGs as Technical Security Baselines

{% hint style="info" %}
Security Technical Implementation Guides (STIGs) translate cybersecurity requirements into product- and technology-specific configuration expectations.
{% endhint %}

### 5.12.2 Security Requirements Guides

{% hint style="info" %}
Security Requirements Guides (SRGs) provide security requirements for technologies, capabilities, or environments where product-specific implementation may vary.
{% endhint %}

### 5.12.3 STIG Compliance Is Necessary but Not Complete Identity Security

{% hint style="info" %}
A domain controller can satisfy its operating-system STIG while dangerous delegation, certificate templates, nested group relationships, federation configuration, or hybrid trust paths remain exploitable.
{% endhint %}

### 5.12.4 Category I, II, and III Findings

{% hint style="info" %}
STIG severity categories provide a mechanism for prioritizing findings but should still be interpreted within the technical and mission context of the affected identity component.
{% endhint %}

### 5.12.5 Open Findings and Identity Criticality

{% hint style="info" %}
An apparently narrow configuration finding may deserve elevated attention when it affects Tier 0 infrastructure or creates a viable attack path into the identity control plane.
{% endhint %}

### 5.12.6 Automated STIG Assessment

{% hint style="info" %}
Automation can improve consistency and scale but cannot replace engineering judgment when applicability, dependencies, mission constraints, inheritance, or effective authority must be evaluated.
{% endhint %}

### 5.12.7 STIG Evidence Must Support RMF

{% hint style="info" %}
STIG and SRG results should feed the broader authorization and continuous-monitoring process rather than becoming a separate compliance universe.
{% endhint %}

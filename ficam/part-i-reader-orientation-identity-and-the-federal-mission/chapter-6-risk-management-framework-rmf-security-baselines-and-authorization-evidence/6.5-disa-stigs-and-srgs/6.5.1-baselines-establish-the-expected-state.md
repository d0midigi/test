# 6.5.1 Baselines Establish the Expected State

SRGs and STIGs are related but serve different functions.

An SRG establishes security requirements for a technology category, capability, or class of systems. A STIG translates applicable requirements into guidance for a particular product or technology implementation. DISA's vendor STIG process makes that relationship explicit: vendor-developed STIGs are written against an applicable published DoD SRG and then processed through DISA's STIG development framework.

The distinction reflects the same requirement-to-implementation chain discussed earlier in this chapter.

The security requirement begins at a level above the product.

The implementation guide expresses how the product should satisfy it.

This is why an administrator should understand the requirement represented by a STIG rule rather than treating the rule as an isolated configuration instruction.

Suppose a rule requires a particular authentication protection.

The value of the rule is not the registry value itself.

The value lies in preventing an authentication condition DoD has determined creates unacceptable exposure.

Likewise, a rule requiring audit events exists because some security-relevant behavior must remain observable. A restriction on remote administration exists because administrative reach affects system exposure. A requirement to disable an obsolete protocol exists because retaining that protocol creates an attack surface inconsistent with the intended baseline.

Understanding the objective becomes particularly important when a system cannot implement the prescribed configuration exactly.

The engineering question then becomes whether the security outcome can still be achieved through an approved alternate or compensating mechanism—not simply whether the administrator can make the scanner stop reporting the finding.

# 2.3.2 Active Directory Does Not Need to Own a Resource to Control Access to It

An important consequence of centralized identity is that Active Directory can influence access to systems it does not technically host.

Consider a domain security group used to authorize access to a shared application.

The application may run on a separate server, use its own database, and have no direct relationship with the Domain Controller beyond authentication and authorization dependencies. Yet if the application grants administrative access to members of a particular domain group, control over that group's membership becomes control over the application's administrative boundary.

The application remains operationally independent.

Its authorization has become identity-dependent.

The same pattern appears throughout enterprise infrastructure.

Virtualization platforms may use domain groups for administrative access. Backup platforms may delegate roles to Active Directory identities. Security Information and Event Management (SIEM) systems may authenticate administrators through the domain. Network devices may rely on RADIUS or TACACS+ infrastructure backed by directory accounts. Certificate-enrollment permissions may be expressed through directory security principals. Remote-access gateways may authorize users through domain membership or federated identity.

From the perspective of an attack path, the distinction between “the system” and “the identity controlling the system” begins to collapse.

The path to the resource may not pass through a software vulnerability in the resource at all.

It may pass through the directory object that controls who is allowed to administer it.

This is one reason an Active Directory security assessment that looks only for privileged accounts will miss significant portions of the real control plane.

The relevant authority may be indirect.

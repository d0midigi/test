# 2.6.3 Assume Breach Applies to Identity Systems Themselves

Identity infrastructure is sometimes treated as the mechanism used to secure everything else while receiving comparatively little scrutiny as an attack surface of its own.

That is dangerous.

Domain Controllers can be compromised. Certification Authorities can be compromised. Federation servers can be compromised. Identity synchronization systems can be compromised. Privileged-access platforms can be compromised. Administrative workstations can be compromised. Cloud administrative identities can be compromised.

An assume-breach model therefore cannot stop at the statement that users and endpoints may fail.

The identity system itself must have failure boundaries.

A compromised member server should not expose reusable Domain Controller credentials.

A compromised federation server should not automatically grant access to Certification Authority private keys.

A compromised cloud administrator should not automatically possess unrestricted on-premises directory authority unless the architecture has deliberately created that relationship.

A compromised synchronization server should be treated according to the actual privilege it possesses in both identity planes rather than its innocuous description as "middleware."

This is where the concept becomes uncomfortable but useful.

Some identity systems are so authoritative that their compromise cannot be meaningfully contained while they remain trusted. If a root Certification Authority private key is stolen, the problem is not merely that a server has been compromised. If the KRBTGT key is exposed, the problem is not merely an account password incident. If an authoritative identity source is manipulated, downstream systems may consume malicious state while behaving exactly as designed.

Assume breach does not promise that every compromise can be contained indefinitely.

It requires the architecture to identify where containment stops and trust restoration must begin.

# 4.1.3 Governance Should Remain Traceable to Real Configuration

The policy-to-technical chain becomes weak when evidence substitutes for reality.

A system-security plan may state that privileged access is restricted.

That statement is not the control.

The control exists in actual identities, group memberships, delegation, authentication restrictions, workstation design, privileged-access systems, and administrative pathways.

Likewise, an implementation statement may say that inactive accounts are disabled according to policy. The security condition exists only if stale accounts are actually identified, governed, disabled, and prevented from quietly reappearing through provisioning or synchronization.

The distinction matters because authorization packages describe systems; they do not secure them.

NIST's RMF explicitly emphasizes traceability between requirements and implemented controls and ties authorization to risk to organizational operations, assets, individuals, other organizations, and the Nation.

For identity infrastructure, that traceability should reach all the way to authoritative state.

If a control says access is limited, the assessor should be able to determine who actually has access.

If a control says privileged functions are separated, the directory should show that separation.

If an implementation says multifactor or certificate authentication protects privileged access, the environment should not retain an undocumented alternate authentication path that defeats the intended assurance.

A technically strong identity program makes its governance claims testable.

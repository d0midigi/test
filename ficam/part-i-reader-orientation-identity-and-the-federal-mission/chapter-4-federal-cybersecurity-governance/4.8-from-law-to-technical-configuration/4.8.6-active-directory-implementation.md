# 4.8.6 Active Directory Implementation

Active Directory implementation is where every preceding layer meets the actual trust system.

A least-privilege requirement becomes a set of groups, permissions, delegation boundaries, and administrative workflows.

A strong-authentication requirement becomes Kerberos policy, PIV or CAC integration, certificate mapping, modern authentication, smart-card enforcement, or another approved mechanism.

An account-management requirement becomes object creation, sponsorship, disablement, provisioning, synchronization, and recertification.

An audit requirement becomes Domain Controller policy, SACLs, Windows events, PKI logs, federation logs, cloud audit data, SIEM ingestion, and detection logic.

A contingency requirement becomes tested forest recovery, protected backups, independent administrative credentials, certificate recovery, federation key replacement, and trust reconstitution.

This is the level at which governance can finally be attacked.

An adversary cannot exploit a paragraph in a policy document.

The adversary exploits the implementation.

That makes Active Directory security a particularly powerful test of whether governance has survived translation.

If policy says privilege is minimized but attack-path analysis reveals ordinary users with indirect Tier 0 control, the implementation has diverged from the intended governance outcome.

If policy requires strong authentication but a legacy protocol provides a weaker parallel route, the architecture has preserved an exception that changes the actual assurance.

If an authorization package says privileged access is tightly controlled but the virtualization platform can administer every Domain Controller from a lower-trust management plane, the represented boundary and the effective boundary are different.

Those discrepancies are where offensive and defensive FICAM operations become valuable.

Offensive analysis tests the trust relationships as they actually exist.

Defensive engineering corrects the architecture.

Assessment establishes evidence that the correction is real.

Governance determines whether the remaining risk is acceptable to the mission.

The policy-to-technical-control chain is complete only when all four agree.

When they do not, the configuration—not the documentation—reveals the truth.

0x02-Stealth Persistence via Nested ACL Manipulation in FICAM Active DirectoryThe problem with most "backdoor" accounts in Active Directory is that they are built like neon signs: a new user suddenly appears in Domain Admins, its SID is pushed into every replicated group-membership cache in the forest, and within minutes every competent SOC is firing alerts. Trying to hide the account inside the Program-Data container only proves that obscurity without control is worthless; the object is still returned by any LDAP query that asks for `"(objectClass=user)"` and the DENY-ACEs that were supposed to cloak it simply made the account more interesting once they were noticed. What defenders need to learn from this is that hiding an object without hiding its authority is the same as dying your hair while leaving your fingerprints on the murder weapon.Attackers drew the opposite lesson: authority can be hidden even when the object itself is in plain sight. The leaf-in-the-forest metaphor is not poetic fluff; it is an engineering requirement. A mid-sized enterprise already contains tens of thousands of security descriptors, most of which are never inspected after the day they were created. If the delegation that grants Domain Admin equivalence can be expressed as two ACL entries buried five hundred lines deep in the discretionary ACL of an innocuous built-in group, the account that ultimately profits from that delegation never needs to carry a privilege group SID in its token. From the point of view of every token-logging tool, the account is an ordinary user. From the point of view of the security auditor who exports `"net group 'Domain Admins' /domain,"` nothing has changed. Yet the moment the attacker chooses, they can add themselves to Terminal Server License Servers, and that group - now empowered to write the member attribute of Domain Admins - becomes a trampoline straight into the highest privilege layer of the entire directory.Defenders who rely on the comforting rhythm of adminSDHolder's hourly reset are the exact target of the second trick. The protection mechanism was designed to stop persistent rogue administrators, but it only protects objects whose adminCount attribute is 1. A group that ships with the operating system, such as Terminal Server License Servers, is not in that protected set; its ACL is stable once changed, and the change replicates to every writable DC without fanfare. The attacker, therefore, performs one edit that looks utterly benign - granting License Servers the right to adjust the membership of Domain Admins and then waits. Prior-Art FailureYou can effectively hide a domain administrator equivalent account inside `CN=Program Data,CN=System` container and denying read access to the object; however, this technique fails operationally:* The account remains visible to any principal that holds the standard read-permissions granted by default to "Authenticated Users" on the naming context.* Deletion is trivial through any LDAP browser or the Microsoft management consoles once the object is located. Consequently, the approach offers no practical concealment.Threat Model and Design GoalsObjective: Obtain an account that can regain Domain Admin rights at will, while never appearing in high-privileged groups, never possessing an explicit ACL on a protected group, surviving hourly ACL resets enforced by adminSDHolder, and minimizing the number of artifacts that are evaluated by routine audits.Hiding Principle - "Leaf in an Autumn Forest"Instead of concealing the account, this technique dissolves the account inside the population of ordinary user objects and chains two low-profile ACL entries that are rarely examined:a. Grant an unprivileged user the right to modify the membership of an inconspicuous built-in group.b. Grant that same built-in group the right to modify the membership of a protected group (e.g., "Domain Admins").Because the backdoor user is never a member of any privileged group, group-membership auditors do not flag it. Because the intermediate group is not protected by adminSDHolder, its ACL is not reset every 60 minutes.Implementation Walk-ThroughStep 1 - Create a vanilla user objet anywhere inside the default Users container.Step 2 - Grant the user the `Write-Members` permission (`GUID: BF9679C0-0DE6-11D0-A285-00AA003049E2, access mask 32, ACE type ADS\_ACETYPE\_ACCESS\_ALLOWED\_OBJECT) on the built-in group CN=Terminal Server License Servers,CN=Builtin.Step 3 – Grant the same built-in group identical Write-Members permission on CN=Domain Admins,CN=Users.Step 4 - (Optional but recommended) - Remove the user from the default "Domain Users" membership to reduce its footprint in token-groups enumeration.Circumventing adminSDHolder ProtectionsObject whose `adminCount` attribute equals `1` inherit their ACL from `CN=AdminSDHolder,CN=System` once per hour.Two persistence strategies exist:1. Set `adminCount=0` on the intermediate group. This is overwritten if the group is ever re-protected.2. Permanently add the required ACE to the AdminSDHolder template itself. The modification is replicated forest-wide and survives indefinitely; few operators inspect this container.Detection and Remediation* Enumerate every ACL on every group that can influence a privileged group (transitive closure of one-hop `Write-Members`).* Alert on non-default trustees that hold `Write-Members` on AdminSDHolder.* Correlate creation events (Event ID 4720) with subsequent ACL changes (Event ID 4670) on Built-In groups.* Force a manual adminSDHolder consistency check (`ldp.exe > RunProtectAdminGroupsTask`) and diff the resultant ACLs against a gold baseline.Extending the PatternThe same nested-authority trick can be applied to GPO link properties, OU ACLs, or attribute-scoped quotas, yielding arbitrarily deep delegation chains that evade simple membership queries.Reference ImplementationsPowerShell and VBScript automation examples are available at:https://ptresearch.blogspot.com/2011/04/backdoor-in-active-directory.htmlhttps://devteev.blogspot.com/2011/02/backdoor-active-directory.html (Russian)

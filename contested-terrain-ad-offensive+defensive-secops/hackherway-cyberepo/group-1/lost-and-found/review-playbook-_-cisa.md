<summary><strong>Rebuild Group Managed Service Accounts (gMSA) (CM0135)</strong></summary>

#### Intended Outcome

Rebuilding group managed service accounts (gMSA) prevents an adversary's attempts at initial compromise and privilege escalation by abusing gMSA.

#### Introduction

Group Managed Service Accounts (gMSA) are accounts used by services and often require elevated privileges. Passwords for gMSA are randomly generated by the Key Distribution Service (KDS) from a root key in AD. Adversaries can compromise managed accounts via pass-the-hash or LDAP exploits and use gMSA permissions. Resetting the password is not always sufficient if the root key has been exposed; rebuilding accounts and generating a new root key is recommended.

#### Preparation

* Identify machines that need service accounts.
* Identify services that need accounts.
* Ensure Active Directory PowerShell module is installed on all machines that the service account needs access to.
* Ensure process logging is enabled.

#### Risks

* Service accounts will be unavailable between disabling and rebuilding; perform outside active hours.
* After creating a root key, a domain controller needs \~10 hours to allow replication before new gMSA creation.
* Rebuilding the root key may cause issues due to caching; consider restarting KDS on domain controllers.

#### Guidance

**Remove old gMSA**

* Identify all gMSA: `Get-ADServiceAccount -Filter *`
* Remove gMSA: `Remove-ADServiceAccount`
* Remove old KDS root key.

**Build new gMSA**

* Create new KDS root key: `Add-KdsRootKey -EffectiveImmediately`
* Restart all domain controllers to avoid caching/replication issues.
* Create security group for accounts and add users/computers (may require reboots).
* Create accounts: `New-ADServiceAccount` (specify security group).
* Install account: `Install-ADServiceAccount`
* Optionally set SPN: `setspn -a <SPN> <USER>`.

**Monitor for gMSA enumeration techniques**

* Monitor for process calls to BloodHound or Mimikatz.
* Monitor for `Get-ADServiceAccount -Filter _-Properties_` command.
* Monitor suspicious PSExec or LDAP activity.
* Monitor access to LSA secrets or modification to `HKLM\SECURITY\Policy\Secrets`.

#### References

* Attacking Group Managed Service Accounts (gMSA) | https://medium.com/@offsecdeer/attacking-group-managed-service-accounts-gmsa-5e9c54c56e49
* Secure group managed service accounts | https://learn.microsoft.com/en-us/entra/architecture/service-accounts-group-managed
* Create the Key Distribution Services KDS Root Key | https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-managed-service-accounts/group-managed-service-accounts/create-the-key-distribution-services-kds-root-key

<summary><strong>Reset Interdomain Trust Account (ITA) Credentials (CM0145)</strong></summary>

#### Intended Outcome

Resetting interdomain trust accounts (ITA) credentials prevents adversary initial access and lateral movement via compromised ITA credentials.

#### Introduction

ITA are objects stored in an authenticating domain that contain trust relationship information. These accounts contain trust secrets maintained by the domain controller with the PDC Emulator FSMO role. Adversaries can compromise ITA in the trusting domain and use its password hash to authenticate in the trusted domain.

#### Preparation

* Identify trust relationships between domains and trust directions.
* Identify which relationships have ITA and which domains host those accounts.

#### Risks

No Risks content identified.

#### Guidance

**Reset ITA credentials**

* Use `netdom experthelp trust` to get appropriate syntax for NetDom.
* Examples:
  * On parent domain: `netdom trust parent domain name /domain:child domain name /resetOneSide /passwordT:password /userO:administrator /passwordO:*`
  * On child domain: `netdom trust child domain name /domain:parent domain name /resetOneSide /passwordT:password /userO:administrator /passwordO:*`
* Only run once; it resets the password twice automatically.

**Monitor for ITA hash compromise techniques**

* Monitor for Mimikatz activity and related command-line parameters.
* Monitor for Rubeus process execution.
* Monitor for Kerberos TGT requests for interdomain trust accounts.

#### References

* Abusing Trust Account$ | https://www.ired.team/offensive-security-experiments/active-directory-kerberos-abuse/abusing-trust-accountusd-accessing-resources-on-a-trusted-domain-from-a-trusting-domain

<summary><strong>Restrict Accounts with Privileged Active Directory (AD) Access from Logging into Endpoints (CM0084)</strong></summary>

#### Intended Outcome

Restricting accounts with privileged AD access from logging into endpoints blocks adversary lateral movement via privileged AD access.

#### Introduction

Accounts with domain privileges should only be used from designated Privileged Access Workstations (PAWs). Blocking privileged accounts (e.g., Domain Admins) from logging into unauthorized endpoints reduces the risk of lateral movement.

#### Preparation

* Assess impact on job activities of affected accounts.
* If containing an adversary, rotate credentials before restricting.
* Verify if the user right is required by a service account; if so, create a gMSA and delegate minimal privileges.

#### Risks

* Removing the ability for a service account to log into an endpoint may disrupt services/processes.

#### Guidance

**Apply Deny Log On User Rights**

Enforce the following restrictions on the account(s) via GPO (Group Policy Editor):

* Deny access to this computer from the network (SeDenyNetworkLogonRight) — include SID S-1-5-114.
* Deny logon as a service (SeDenyServiceLogonRight)
* Deny log on as a batch job (SeDenyBatchLogonRight)
* Deny log on locally (SeDenyInteractiveLogonRight)
* Deny log on through Remote Desktop (SeDenyRemoteInteractiveLogonRight)

Location: Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > User Rights Assignment

Use PowerShell as an alternative and link the GPO appropriately.

**Remove Unauthorized Log On User Rights**

Remove equivalent 'log on' user rights:

* SeNetworkLogonRight, SeServiceLogonRight, SeBatchLogonRight, SeInteractiveLogonRight, SeRemoteInteractiveLogonRight

Force update: `Gpupdate /force`

<summary><strong>Enable Active Directory (AD) Protected Users Security Group (CM0018)</strong></summary>

#### Intended Outcome

Enabling the AD Protected Users security group restricts adversary lateral movement using protected user credentials.

#### Introduction

Protected Users group applies non-configurable protections to members, designed to proactively secure accounts. Only removing an account from the group modifies these protections.

#### Preparation

* Confirm primary domain controller is Windows Server 2012 R2 or later.
* Confirm client computers are Windows 8.1 or Windows Server 2012 R2 or later.

#### Risks

* Can break legitimate functionality.
* Adding Managed Service Accounts to Protected Users will break Kerberos Constrained Delegation (KCD).
* Not recommended for service accounts that depend on KCD.

#### Guidance

* Add necessary accounts (e.g., Admin) to Protected Users Group.
* Verify membership and monitor authentication/failure logs.
* Best practices:
  * Protections may replicate to older OSes if a 2012 R2+ PDC emulator exists.
  * Protections do not work for client devices below Windows 8.1.
  * Never add all privileged accounts to Protected Users to avoid lockout.

#### References

<summary><strong>Remove Extraneous and Stale Accounts (CM0112)</strong></summary>

#### Intended Outcome

Removing extraneous and stale accounts blocks or restricts adversary initial access, persistence, defense evasion, and lateral movement.

#### Introduction

Extraneous/stale accounts (no longer active) can be unmonitored and targeted by attackers. Former employees' accounts left active are additional risks.

#### Preparation

* Identify org procedures for inactive accounts and de-provisioning timelines.

#### Risks

No Risks content identified.

#### Guidance

* Audit AD users based on password age and last logon. Example PowerShell (180 days): `Get-ADUser -Filter '(PasswordLastSet -lt $d) -or (LastLogonTimestamp -lt $d)' -Properties PasswordLastSet,LastLogonTimestamp | ft Name,PasswordLastSet,@{N="LastLogonTimestamp";E={[datetime]::FromFileTime($_.LastLogonTimestamp)}}` where `$d = [DateTime]::Today.AddDays(-180)`
* Disable found accounts and move to a separate OU.
* Consider deleting accounts per organization policy (weigh operational impact).

#### References

* https://learn.microsoft.com/en-us/services-hub/unified/health/remediation-steps-ad/regularly-check-for-and-remove-inactive-user-accounts-in-active-directory

<summary><strong>Disable Service Account Interactive Login (CM0041)</strong></summary>

#### Intended Outcome

Disabling service account interactive login restricts adversary lateral movement using service accounts.

#### Introduction

Interactive logon authenticates input credentials; service accounts should not perform interactive logons.

#### Preparation

* Disable compromised user account.
* Disconnect affected systems from the network.

#### Risks

* Errors can render mitigation ineffective.
* If an adversary has admin rights, they may configure services to run as System; evict adversary first.
* May not stop all ongoing activity; adversaries can bypass GPO by brute-force or default passwords.

#### Guidance

* Use GPO or Local Security Policy console to deny interactive logons.
* Best to assign via GPO (Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > User Rights Assignment).
* Add accounts to "Deny log on locally" and "Deny log on through Terminal Services".
* Policies apply after machines reboot; they take priority over allow rights.

<summary><strong>Disable On-Premise AD Accounts with Privileged Roles in Entra ID (CM0124)</strong></summary>

#### Intended Outcome

Disabling privileged on-premises AD accounts in Entra ID prevents adversary persistence or privilege escalation via admin/domain accounts.

#### Introduction

On-premises domains often integrate with Entra ID; compromised on-premises admin accounts may authenticate with Entra ID to access managed domain resources.

#### Preparation

* Identify on-premises AD accounts with privileged roles in Entra ID.
* Identify de-provisioning procedures and emergency access accounts.

#### Risks

* Admins may be locked out; use emergency access accounts if needed.
* Accounts removed on-prem do not automatically remove from Entra ID.

#### Guidance

* Find Entra admin roles: Identity > Roles & admins > Roles & admins > Assignments.
* Manually disable on-prem user: `Disable-ADAccount -Identity <account_to_disable>` and reset password twice.
* Manually disable Entra users or remove roles via Microsoft Entra admin center (Identity > Users > All users).
* Remove users from privileged accounts via GPO: Computer Configuration > Preferences > Control Panel Settings > Local Users and Groups; use Update action and remove from group; link policy and run `gpupdate /force`.

<summary><strong>Restrict and Monitor Domain Accounts with Local Administrator Access to Workstations (CM0060)</strong></summary>

#### Intended Outcome

Restricting and monitoring domain accounts with local administrator access prevents privilege escalation and credential access.

#### Introduction

Domain accounts signing into workstations may have cached credentials. If a workstation is compromised, cached credentials can be retrieved and used for lateral movement.

#### Preparation

* Consult operations and personnel about necessary local admin actions and device permissions.

#### Risks

No Risks content identified.

#### Guidance

* Monitor for credential dumping and staging activity (e.g., `reg save`, `vssadmin`, lsass.exe access). Use Windows Security Event ID 4656 and others to identify suspicious behavior.
* Monitor for PsExec, SMB connections, and related logs (event IDs: 5145, system log 7045).
* Restrict local admin access where possible and block internal device connections that enable pivoting.

<summary><strong>Restrict Domain Admin User Rights and Monitor Protected Users on Workstations (CM0094)</strong></summary>

#### Intended Outcome

Restricting Domain Admin user rights and monitoring Protected Users on workstations/servers reduces the likelihood of privileged credential access via credential dumping.

#### Introduction

Adversaries dump credentials iteratively to escalate privileges. Preventing Domain Admin credentials from being cached on member workstations/servers reduces credential exposure.

#### Preparation

* Review accounts in Domain Administrator group; ensure only necessary accounts exist.
* Consider removing Domain Administrators from local Administrator groups where appropriate.

#### Risks

* Identify scenarios where Domain Admins need access to member systems and provide alternatives to avoid disruption.

#### Guidance

* Configure GPO to add Domain Administrators to the following deny list:
  * Deny access to this computer from the network
  * Deny log on as a batch job
  * Deny log on as a service
  * Deny log on locally
  * Deny log on through Remote Desktop Service user rights
* Apply GPO to appropriate OUs.
* Monitor event id 4624 - type 2 for interactive logons.

<summary><strong>Revoke Existing Administrator Permissions and Deploy New Administrator Accounts (CM0118)</strong></summary>

#### Intended Outcome

Revoking existing administrator accounts and permissions and deploying new ones removes adversary persistence, lateral movement, and privilege escalation using existing admin credentials.

#### Introduction

Administrator accounts are high-value targets. To evict an adversary, privileged accounts need new credentials, tokens, and access control.

#### Preparation

* Identify all administrator/privileged accounts.
* Determine timing to minimize business disruption.
* Locate administrator provisioning policy.

#### Risks

* Mass credential resets disrupt business; schedule during slower times.
* Improper provisioning may lock out admins; peer review configs before rollout.

#### Guidance

**Revoke existing permissions**

* Use GPO: Computer Configuration > Preferences > Control Panel Settings > Local Users and Groups.
* Add rule, choose Update action, select group, add administrators, choose Remove from this group action.
* Link GPO to OU and run `gpupdate /force`.

**Create and deploy new accounts**

* Use User Administrator role in Microsoft Entra admin center: Identity > Users > All users > New user > Create new user
* Fill fields and assign necessary roles.

#### References

* https://techcommunity.microsoft.com/t5/microsoft-security-experts-blog/effective-strategies-for-conducting-mass-password-resets-during/ba-p/4159408
* https://learn.microsoft.com/en-us/entra/fundamentals/how-to-create-delete-users
